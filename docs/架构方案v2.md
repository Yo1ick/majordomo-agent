## 一、系统概述

基于多 Agent 协作的个人生活管家系统。通过飞书 Bot 与用户交互，管理记账、健康/健身、资产三大领域。

### 技术栈

| 层 | 选型 | 说明 |
|----|------|------|
| 交互层 | 飞书 Bot | 唯一入口，Webhook 接收消息 |
| Agent 框架 | 待定（Q1） | 待确认 OpenClaw / NanoClaw |
| 本地模型 | Gemma 3 E4B | 高频简单任务（意图分类、格式提取） |
| 云端模型 | Claude / Gemini API | 复杂任务（饮食规划、健身计划） |
| 存储 | SQLite (WAL) | 单文件，轻量，本机部署 |
| 部署 | Mac Mini | webhook 触发 + cron 兜底 |

### 设计原则

- **飞书先行，API 层留口，前端后补**
- **业务逻辑与交互层分离**（不耦合飞书 SDK）
- **Agent 间松耦合**（通过事件表通信）
- **本地模型处理高频任务，云端 API 处理复杂任务**

## 二、Agent 架构

### 2.1 总体结构

```
飞书消息
   ↓
┌─────────────┐
│   Router     │  意图识别 + 分发（本地模型）
└─────┬───────┘
      ├──────────────┬──────────────┐
      ↓              ↓              ↓
┌───────────┐  ┌───────────┐  ┌───────────┐
│ Bookkeeper│  │Health Coach│  │Asset Mgr  │
│  记账管家  │  │ 健康教练   │  │ 资产管家   │
└─────┬─────┘  └───────────┘  └───────────┘
      ↓
┌───────────┐
│Bill Parser│  子 Agent：账单识别
└───────────┘
```

### 2.2 Router（消息路由）

**职责**：接收飞书消息，识别意图，分发给对应 Agent。

| 输入 | 意图 | 分发目标 |
|------|------|----------|
| 账单图片 | expense_record | Bookkeeper |
| "今天跑了5公里" | exercise_log | Health Coach |
| "家里鸡蛋还剩多少" | asset_query | Asset Manager |
| "这个月花了多少" | expense_query | Bookkeeper |
| "推荐今晚吃什么" | meal_recommend | Health Coach |
| "Netflix 下个月到期" | subscription_alert | Asset Manager |

**实现**：本地 Gemma E4B 做分类，不需要云端 API。

### 2.3 Bookkeeper（记账管家）

**职责**：管钱的流水，不管钱在哪。

**基础功能**：
- 接收账单（图片/文字），调用 Bill Parser 解析
- 写入支出记录（expenses + expense_items）
- 按 item 类别发事件给其他 Agent
- 月度/周度账单汇总
- 消费趋势分析
- 分类统计（"外卖占比"、"交通花费"）
- 预算管理（可选，后期）

**子 Agent — Bill Parser**：
- 输入：账单图片
- 输出：`{merchant, total_amount, items[], occurred_at}`
- 只做识别，不写库

### 2.4 Health Coach（健康教练）

**职责**：一切跟"身体"相关的事。从被动记录到主动规划。

**基础功能**：

_记录模块（tracker）_：
- 饮食记录（手动/从 Bookkeeper 事件自动创建）
- 运动记录（文字/运动截图 OCR）
- 睡眠记录（手环截图 OCR / 手动）
- 每日营养汇总（热量、蛋白质、碳水、脂肪）

_规划模块（planner）_：
- 健身计划制定（碳循环、增肌/减脂周期）
- 每日饮食推荐（基于菜谱库 + 冰箱库存 + 营养目标）
- 训练计划执行跟踪
- 碳循环排期（高碳日/低碳日/休息日）

_数据支撑_：
- 食材库（food_library）：LLM 冷启动 + 运行时补漏
- 菜谱库（recipes）：用户会做的菜，关联食材和营养
- 健身目标配置：当前阶段、目标体重、每日 TDEE

### 2.5 Asset Manager（资产管家）

**职责**：管"你有什么"——实物、钱、虚拟订阅。

**基础功能**：

_金融资产_：
- 账户管理（微信/支付宝/银行卡余额）
- 负债管理（房贷/信用卡/分期）
- 投资管理（基金/股票，记录市值）
- 净资产计算

_实物资产_：
- 食材库存（从 Bookkeeper 事件自动入库）
- 日用品/电子产品追踪
- 库存扣减（被 Health Coach 消费时）

_虚拟资产（新增）_：
- 订阅管理（Netflix/iCloud/健身房/域名...）
- 续费周期 + 到期日
- 到期前飞书提醒
- 月度订阅费用汇总

## 三、业务流程

### 3.1 核心流程：拍一张超市小票

```
用户在飞书发小票图片
      ↓
Router → 识别为 expense_record → 分发给 Bookkeeper
      ↓
Bookkeeper 调用 Bill Parser
      ↓
Bill Parser OCR + 结构化：
  {永辉超市, ¥86.50, [鸡胸肉×2, 洗洁精×1, 可乐×3], 2026-04-08}
      ↓
Bookkeeper 写入 expenses + 3 条 expense_items
      ↓
按 category 发事件（agent_events 表）：
  ├── 鸡胸肉 (food_ingredient) → Asset Manager（食材入库）
  ├── 洗洁精 (consumable)      → Asset Manager（日用品入库）
  └── 可乐 (food_delivery)     → Health Coach（记饮食）
      ↓
各 Agent 消费事件，处理后飞书推确认卡片
```

### 3.2 核心流程：每日饮食推荐

```
每天早上 8:00 cron 触发 Health Coach
      ↓
1. 读取当前健身计划 → 今天是高碳日
2. 计算今日目标：2200 kcal, 蛋白质 150g, 碳水 280g
      ↓
3. 查 Asset Manager 食材库存 → 冰箱有鸡胸肉、西兰花、米饭、鸡蛋
4. 匹配菜谱库 → 筛选食材满足的菜
5. 组合三餐方案，满足营养目标
      ↓
6. 飞书推送：
   "今日高碳日 🎯 2200kcal
    早餐：鸡蛋炒饭 + 牛奶
    午餐：鸡胸肉西兰花 + 米饭 200g
    晚餐：番茄鸡蛋面
    蛋白质 152g | 碳水 275g | 脂肪 68g"
```

### 3.3 核心流程：订阅到期提醒

```
每天 cron 扫描 virtual_assets
      ↓
筛选 next_renewal_date <= 今天 + 7天
      ↓
飞书推送：
  "以下订阅即将到期：
   - Netflix ¥35/月，4月15日续费
   - iCloud 200GB ¥21/月，4月18日续费
   需要取消的请回复编号"
```

### 3.4 核心流程：查询

```
用户："这个月外卖花了多少"
      ↓
Router → expense_query → Bookkeeper
      ↓
SELECT SUM(total_amount) FROM expenses
WHERE category = 'food_delivery'
  AND occurred_at >= '2026-04-01'
  AND deleted_at IS NULL
      ↓
飞书回复："4月外卖共消费 ¥1,234.50，占总支出 38%"
```

### 4.2 分层架构

每个 Agent 内部统一三层：

```
┌─────────────────────────────────────┐
│  Agent 层（agent.py）                │  接收消息，编排流程
├─────────────────────────────────────┤
│  Service 层（service.py）            │  纯业务逻辑，不依赖飞书
├─────────────────────────────────────┤
│  Repository 层（repository.py）      │  数据访问，SQL 封装
└─────────────────────────────────────┘
```

**关键约束**：
- Service 层不 import 任何飞书相关代码
- Repository 层只做 CRUD，不含业务判断
- Agent 层负责编排 Service + 飞书交互

### 5.1 新增：食材库

```sql
CREATE TABLE IF NOT EXISTS food_library (
    id          TEXT PRIMARY KEY,
    name        TEXT NOT NULL,
    aliases     TEXT,                    -- JSON: ["鸡脯肉","chicken breast"]
    category    TEXT,                    -- 肉类/蔬菜/主食/调料
    calories    REAL NOT NULL,           -- kcal / 100g
    protein_g   REAL,
    carbs_g     REAL,
    fat_g       REAL,
    fiber_g     REAL,
    sodium_mg   REAL,
    source      TEXT NOT NULL,           -- llm_generated / manual / usda / china_cdc
    verified    INTEGER NOT NULL DEFAULT 0,
    created_at  TEXT NOT NULL DEFAULT (datetime('now')),
    updated_at  TEXT
);

CREATE INDEX idx_food_name ON food_library(name);
```

### 5.2 新增：菜谱库

```sql
CREATE TABLE IF NOT EXISTS recipes (
    id          TEXT PRIMARY KEY,
    name        TEXT NOT NULL,
    servings    INTEGER DEFAULT 1,
    cook_time   INTEGER,                 -- 分钟
    difficulty  TEXT CHECK(difficulty IN ('easy','medium','hard')),
    tags        TEXT,                    -- JSON: ["高蛋白","低碳","快手"]
    note        TEXT,
    created_at  TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE IF NOT EXISTS recipe_ingredients (
    id          TEXT PRIMARY KEY,
    recipe_id   TEXT NOT NULL REFERENCES recipes(id),
    food_id     TEXT NOT NULL REFERENCES food_library(id),
    amount_g    REAL NOT NULL,
    optional    INTEGER NOT NULL DEFAULT 0

```

### 5.3 新增：健身计划

## 六、运行模型

### 6.1 进程架构

```
Mac Mini 上运行：

[飞书 Webhook Server]     ← 常驻，接收飞书消息
        ↓ 调用
[Router]                  ← 按需触发
        ↓ 调用
[Agent 处理逻辑]           ← 按需触发，非常驻

[Cron Jobs]               ← 定时任务
  - 每小时：扫描 agent_events 未消费事件（兜底）
  - 每小时：扫描 pending_confirmations 过期记录
  - 每天 8:00：饮食推荐
  - 每天 9:00：订阅到期提醒
  - 每天 3:00：数据库备份 → iCloud
```

### 6.2 错误恢复

- Webhook Server 用 pm2 / launchd 守护，崩溃自动重启
- Agent 处理失败 → agent_events.retry_count + 1，cron 下次重试
- 重试 3 次仍失败 → status 改为 dead，飞书通知用户
