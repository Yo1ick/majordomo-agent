# 建设性建议

> 审查日期：2026-04-08  
> 基于：架构审查意见.md、schema.sql、SESSION.md

---

## 一、Schema 层面

### 1. `nutrition_daily.date` 的 UNIQUE 约束缺少 `user_id`

```sql
-- 现在：date TEXT NOT NULL UNIQUE
-- 问题：多用户时，同一天只能有一条记录
-- 建议：
UNIQUE(user_id, date)
```

这和多用户/家庭支持的设计直接冲突。

### 2. `expenses` 缺少 `account_id` 关联

`accounts` 表已经建了（微信/支付宝/银行卡），但 `expenses` 没有字段记录"这笔钱从哪个账户出的"。如果要做账户余额自动扣减或对账，需要加 `account_id TEXT REFERENCES accounts(id)`。

### 3. `liabilities` 的 `interest_rate` 用基点存储容易误解

注释写 `4500 = 4.5%`，但金融行业中 1 基点 = 0.01%，所以 4500 基点 = 45%。建议改用万分比（`450 = 4.50%`）或直接存 REAL（`4.5` 表示 4.5%），并在注释中明确单位。

### 4. 软删除无索引

多张表用 `deleted_at` 做软删除，但查询时 `WHERE deleted_at IS NULL` 没有覆盖索引。数据量大了之后全表扫描。建议给常查询表加部分索引：

```sql
CREATE INDEX idx_expenses_active ON expenses(user_id, occurred_at) WHERE deleted_at IS NULL;
```

### 5. `agent_events` 缺少幂等保障

`message_id UNIQUE` 可以防重，但消费端没有幂等标记。如果 intake-tracker 消费了一个事件但处理到一半崩溃，重试时会重复写入 meals。建议加 `processed_at` 字段或在目标表加 `source_event_id UNIQUE` 做幂等。

## 二、架构层面

### 6. 缺少统一的消息路由层

现在飞书消息进来后直接到 bookkeeper，但实际场景中用户可能发：

- 账单图片 → bookkeeper
- "今天跑了5公里" → intake-tracker
- "家里鸡蛋还有多少" → asset-manager
- "这个月花了多少" → 查询，不属于任何 agent

建议在三个 agent 之上加一个 **router agent** 或 **dispatcher**，负责意图识别和分发。这比让用户在飞书里选菜单更自然。

### 7. Agent 间通信只有单向事件，缺少回调机制

当前设计：bookkeeper 写事件 → intake-tracker 消费。但如果 intake-tracker 处理失败需要反馈呢？比如 "无法识别食物热量，需要用户确认"，这个确认结果怎么回传？

建议 `agent_events` 加 `reply_to` 字段，或者让 `pending_confirmations` 支持跨 agent 的确认流。

### 8. 没有定义 Agent 的运行模型

三个 agent 是长驻进程轮询 `agent_events`？还是被飞书 webhook 触发？还是 cron 定时跑？这决定了：

- 延迟：长驻 < webhook 触发 < cron
- 资源：Mac Mini 上跑 3 个常驻进程是否合理
- 错误恢复：进程崩了谁来重启

建议明确写出来。如果是 Mac Mini 部署，推荐 **webhook 触发 + cron 兜底** 的混合模式。

## 三、产品层面

### 9. 缺少"查询"能力的设计

整个架构侧重"录入"（记账、记食物、记资产），但对"查"的场景没有设计：

- "这个月外卖花了多少"
- "上周蛋白质摄入够不够"
- "家里还有什么快过期的"

这些查询是日常高频操作。建议把查询作为第一优先级的功能来设计，而非附属功能。

### 10. `bill-parser` 的 OCR 方案未明确

这是整个系统的入口，但方案里没写用什么做 OCR：

- 飞书原生图片识别？
- 第三方 API（百度 OCR / Google Vision）？
- 本地模型？

不同方案在准确率、成本、隐私上差异很大。建议尽早做 spike，用 20 张真实账单跑一轮评估。

---

## 四、优先级建议

当前计划是 `bill-parser → bookkeeper → asset-manager → intake-tracker`，建议调整为：

1. **先回答 Q1 和 Q5**（Agent 框架 + 飞书接入方式），这两个决定了整个技术底座
2. **Router/Dispatcher** — 飞书消息入口，哪怕初版只做简单规则分发
3. **bookkeeper + bill-parser** — 最核心、最高频的功能
4. **查询功能** — 立刻能用，用户体感好
5. **intake-tracker → asset-manager** — 依赖 bookkeeper 的事件，放后面

---

## 总结

Schema 做得不错，bug 修复和 CHECK 约束都到位了。主要短板在 **架构的运行时模型不清晰**（谁触发谁、进程怎么跑）和 **产品侧缺少查询场景的设计**。建议先把 Q1/Q5 定下来再动手写代码。
